## 0. Цель дополнений

- **Единый механизм** — нет захардкоженных экранов, всё из метаданных
- **Проверка концепции** — если SDUI может рендерить формы для ядровых сущностей, значит он универсален
- **Расширяемость** — если завтра добавим новую ядровую сущность, форма для неё появится автоматически
- **Нет дублирования** — один движок для всех форм  

---

## 1. Обоснование расширения

ТЗ v3.1 §19 «Критерии готовности v0.1» содержит пункт:

> «Можно настроить новый тип документа **без программирования**»

Однако в текущей реализации метаданные создаются только через команды `metadata.entity_type.create` по RPC, что требует знания контракта и не является «настройкой без программирования» для конечного пользователя.

Данное расширение добавляет три фазы **перед Фазой 15** (CSV-экспорт, HTML-печатные формы) для закрытия этого разрыва:

- **Фаза 15pre-1** — Системные метаданные (засеиваются при инициализации платформы)
- **Фаза 15pre-2** — SDUI-рендеринг ядровых сущностей (проверка концепции)
- **Фаза 15pre-3** — Редактор метаданных в клиенте + экспорт/импорт

---

## 2. Новые фазы

### Фаза 15pre-1: Системные метаданные

**Цель:** Засеивать метаданные для ядровых сущностей (компании, пользователи, роли, сами метаданные) при инициализации платформы через `system.bootstrap`.

**Требования:**

1. Системные метаданные **глобальные** (не привязаны к компаниям) — иначе админ не сможет создать новую компанию через интерфейс.
2. Засеиваются **однократно** при `system.bootstrap` (одна точка сидирования).
3. Не могут быть удалены через UI (только через API/скрипт).
4. Могут быть отредактированы администратором (добавление полей, состояний).

**Модель данных:**
Добавить поле `is_system: bool` в `entity_types` (по умолчанию `false`).  
Системные типы: `company`, `user`, `role`, `entity_type`, `entity_field`, `entity_state`, `entity_transition`.

**Изменения в коде:**

- `core-domain/src/metadata.rs`: добавить `is_system: bool` в `EntityType`.
- `core-infrastructure/src/surreal_metadata_repository.rs`: учесть `is_system` при ensure-семантике.
- `core-application/src/bootstrap.rs`: вызвать `seed_system_metadata()` после `seed_system_roles_and_policies()`.
- Новая функция `seed_system_metadata()` в `core-application/src/metadata_seed.rs`: создаёт системные типы с полями/состояниями.

**Команды:**
Нет новых команд. Системные метаданные создаются внутренне в `bootstrap_platform()`.

**Критерии приёмки:**

- ✅ После `system.bootstrap` в БД существуют системные типы сущностей.
- ✅ Системные типы имеют `is_system = true`.
- ✅ Повторный `system.bootstrap` не создаёт дублей (ensure-семантика).
- ✅ Интеграционные тесты `phase_bootstrap` проходят (добавить проверку системных метаданных).

### Фаза 15pre-2: SDUI-рендеринг ядровых сущностей

**Цель:** Проверить концепцию SDUI на ядровых сущностях — клиент рендерит формы для компаний, пользователей, ролей из системных метаданных.

**Требования:**

1. Клиент рендерит каталоги и формы для `company`/`user`/`role` через `ObjectFormScreen` (без захардкоженных экранов).
2. Роуты: `/catalog/company`, `/object/company/:id/edit`, аналогично для `user`/`role`.
3. Проверить, что SDUI-движок корректно обрабатывает все типы полей (reference, enum, array, etc.).
4. Навигация: добавить пункты «Компании», «Пользователи», «Роли» в `module.navigation` (как системный модуль `platform`).

**Изменения в коде:**

- `2c_client/lib/screens/`: нет новых экранов (используется `CatalogScreen`/`ObjectFormScreen`).
- `2c_client/lib/core/router.dart`: добавить роуты для системных сущностей.
- `2c_client/lib/providers/sdui_providers.dart`: добавить провайдеры для системных схем.
- Сервер: добавить системный модуль `platform` с навигацией (компании/пользователи/роли).

**Команды:**
Нет новых команд. Используется существующий `module.navigation` + системные метаданные.

**Критерии приёмки:**

- ✅ Каталог компаний рендерится из системных метаданных.
- ✅ Форма создания/редактирования компании собирается из полей схемы.
- ✅ Аналогично для пользователей и ролей.
- ✅ Деплинки `/catalog/company`, `/object/company/:id/edit` работают.
- ✅ Live-прогон: создать компанию через SDUI-форму, увидеть её в каталоге.
- ✅ Тесты клиента: +10 (проверка рендеринга системных сущностей).

### Фаза 15pre-3: Редактор метаданных

**Цель:** Предоставить администратору UI для создания/редактирования типов сущностей + экспорт/импорт метаданных в файл.

**Требования:**

1. CRUD-экраны для `entity_type`/`entity_field`/`entity_state`/`entity_transition` в клиенте.
2. Доступно только пользователям с ролью `admin` (политика `metadata.manage`).
3. Экспорт метаданных типа в JSON-файл (команда `metadata.export`).
4. Импорт метаданных из JSON-файла (команда `metadata.import`).
5. Валидация при импорте (проверка структуры, дубликатов).

**Модель данных:**
Нет изменений. Используются существующие коллекции `entity_types`/`entity_fields`/`entity_states`/`entity_transitions`.

**Изменения в коде:**

- Сервер:
  - `apps/platform-server/src/commands.rs`: добавить команды `metadata.export`/`metadata.import`.
  - `core-application/src/ports.rs`: добавить методы `export_metadata()`/`import_metadata()` в `MetadataRepository`.
  - `core-infrastructure/src/surreal_metadata_repository.rs`: реализовать экспорт/импорт.
- Клиент:
  - `2c_client/lib/screens/metadata_editor_screen.dart`: новый экран для редактирования метаданных.
  - `2c_client/lib/services/metadata_service.dart`: добавить методы `exportMetadata()`/`importMetadata()`.
  - `2c_client/lib/core/router.dart`: добавить роут `/metadata/editor/:entityType`.

**Команды:**

- `metadata.export {entity_type_code}` → возвращает JSON со схемой типа (поля/состояния/переходы).
- `metadata.import {json_data}` → создаёт/обновляет тип сущности из JSON (ensure-семантика).

**Критерии приёмки:**

- ✅ Админ может создать новый тип сущности через UI.
- ✅ Админ может добавить поля/состояния/переходы через UI.
- ✅ Экспорт метаданных в JSON-файл работает.
- ✅ Импорт метаданных из JSON-файла работает (с валидацией).
- ✅ Системные метаданные нельзя удалить через UI (только редактировать).
- ✅ Тесты: +15 (сервер) +10 (клиент).

## 3. Изменения в модели данных

### 3.1. `entity_types` — добавить поле `is_system`

```rust
pub struct EntityType {
    pub id: Uuid,
    pub company_id: Option<Uuid>,  // None для системных типов
    pub code: String,
    pub name: String,
    pub kind: EntityKind,
    pub is_system: bool,           // НОВОЕ: true для системных типов
    pub metadata_version: u32,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

## Миграция:

UPDATE entity_types SET is_system = false WHERE is_system IS NULL;

## 3.2. Индексы

Добавить индекс для быстрого поиска системных типов:

DEFINE INDEX idx_entity_types_is_system ON entity_types FIELDS is_system;

## 6. Риски и допущения

### 6.1. Риски

    Миграция существующих данных: если в БД уже есть entity_types без поля is_system, нужна миграция.
    Конфликт кодов: системные типы (company/user/role) могут конфликтовать с пользовательскими типами с теми же кодами.
    Решение: системные типы имеют company_id = null, пользовательские — company_id = <UUID>. Уникальность по (code, company_id).

### 6.2. Допущения

    Системные метаданные не могут быть удалены через UI (только через API/скрипт).
    Экспорт/импорт работает только для пользовательских метаданных (системные не экспортируются).
    Редактор метаданных доступен только администраторам (роль admin).

Оценка трудозатрат: 2–3 недели.
Приоритет: Высокий (блокирует критерий готовности v0.1).
